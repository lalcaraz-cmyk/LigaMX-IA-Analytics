# LigaMX IA Analytics - AI Engine

## 1. Purpose

This document defines the complete AI architecture for LigaMX IA Analytics. It covers analytic models, feature engineering, training pipelines, evaluation metrics, explainability, and continuous learning.

It is intended to guide AI developers, data scientists, and engineers building prediction and simulation services that integrate with the broader system architecture in `06_ARCHITECTURE.md`.

## 2. AI Engine Objectives

- Deliver high-quality probability estimates for Liga MX matches.
- Generate calibrated expected goals and score distributions.
- Support transparent model governance and versioning.
- Enable simulation and scenario analysis.
- Provide explainable outputs and audit trail integration.

## 3. AI Architecture Overview

The AI Engine is composed of three logical layers:
- Feature Engineering Layer
- Model and Simulation Layer
- Evaluation and Governance Layer

The feature pipeline operates in training and inference modes with identical transformations. Models are packaged as versioned artifacts. Governance tracks dataset snapshots, training metadata, and deployment state.

## 4. Feature Engineering

### 4.1 Core Feature Categories

- **Match features**: home/away team IDs, competition stage, rest days, venue category.
- **Team features**: dynamic Elo rating, home advantage, offensive and defensive coefficients.
- **Market features**: bookmaker implied probability, line values, market momentum.
- **Context features**: weather, travel distance, fixture congestion.
- **Derived features**: expected goal coefficients, form indexes, head-to-head strength.

### 4.2 Feature Pipeline Requirements

- The pipeline must be deterministic and reproducible.
- Training and inference transformations must be versioned.
- Missing values must be handled explicitly with fallback defaults.
- Feature generation must support incremental updates for new match data.

### 4.3 Data Preparation

- Historical match and market data are joined by `match_id`.
- Temporal leakage is prevented by using only data available before a match.
- Engineered features are stored with dataset snapshot references.

## 5. Model Families

### 5.1 Statistical Models

#### 5.1.1 Poisson Model

- Uses separate attack and defense rates for home and away teams.
- Estimates expected goals using Poisson distributions.
- Serves as a baseline and analytic engine for scoreline generation.

#### 5.1.2 Bivariate Poisson Model

- Extends marginal Poisson distributions with covariance.
- Captures scoreline correlation caused by match dynamics and low-scoring games.
- Preferred for score distribution modeling in `CorrectScore` markets.

#### 5.1.3 Dixon-Coles Model

- Applies time-weighted likelihood adjustments for low scorelines.
- Improves probability estimates for 0-0, 1-0, 0-1, and 1-1 outcomes.
- Used in calibration-sensitive prediction submodels.

### 5.2 Machine Learning Models

- **LightGBM**: gradient boosting for tabular features with strong performance and configurable explainability.
- **XGBoost**: robust tree-based learner for binary and multiclass probability outputs.
- **CatBoost**: supports categorical features and ordered boosting.
- **Linear models**: logistic regression or elastic net for calibration baselines.

### 5.3 Hybrid Models

- Combine analytic expected goals with tree-based probability models.
- Use Poisson-derived features inside ensemble learners.
- Reduce variance by merging statistical and machine learning outputs.

## 6. Prediction Pipeline

### 6.1 Expected Goals Engine

The Expected Goals Engine produces:
- `expected_goals_home`
- `expected_goals_away`

It uses team strength features, home advantage, and match context. Output enters score distribution and probability modules.

### 6.2 Probability Estimation

The probability module uses expected goals and additional features to estimate:
- home win probability
- draw probability
- away win probability

It includes calibration and market adjustment to align with bookmaker signals.

### 6.3 Score Distribution

Score distribution is generated by:
- analytic Poisson models,
- bivariate Poisson models,
- Dixon-Coles adjustments,
- Monte Carlo simulation for scenario aggregation.

Output is stored as a probability map keyed by scoreline.

### 6.4 Market Edge and Kelly

The model output feeds the EV calculator:
- compute implied probability from odds,
- calculate raw edge,
- calculate expected value,
- derive Kelly fraction.

This output is used by `03_BUSINESS_RULES.md` and the portfolio service.

## 7. Training Pipeline

### 7.1 Pipeline Stages

- Data ingestion and validation.
- Feature engineering and snapshot capture.
- Model training with cross-validation.
- Evaluation on holdout seasons.
- Artifact packaging and metadata storage.

### 7.2 Cross Validation

- Use season-aware folds to avoid temporal leakage.
- Preserve chronological order in each fold.
- Evaluate on out-of-sample matches from held-back seasons.

### 7.3 Hyperparameter Optimization

- Use Optuna for tuning LightGBM, XGBoost, and CatBoost.
- Optimize for log loss and calibration metrics.
- Track hyperparameter configurations in model metadata.

### 7.4 Model Registry

- Store `ModelVersion` metadata, training parameters, dataset snapshot references, and evaluation results.
- Support `draft`, `staging`, `production`, and `retired` statuses.
- Capture release notes and governance decisions.

## 8. Evaluation Metrics

### 8.1 Predictive Quality

- **Accuracy**: correct match outcome rate.
- **Log Loss**: penalty for probability errors.
- **Brier Score**: mean squared probability error.
- **Calibration**: ECE and reliability diagrams.
- **ROC AUC**: for binary market probabilities.

### 8.2 Betting Performance

- **Expected Value Capture Rate**: ratio of positive EV recommendations that outperform the market.
- **ROI**: return on investment for simulated and production bets.
- **Maximum Drawdown**: worst cumulative loss period.

### 8.3 Operational Metrics

- **Inference Latency**: time per prediction request.
- **Task Throughput**: number of backtests or simulations processed.
- **Drift Detection**: performance deviation vs. baseline.

## 9. Calibration

### 9.1 Calibration Techniques

- Reliability diagrams to compare predicted probabilities with observed frequencies.
- Isotonic regression or Platt scaling for post-hoc calibration.

### 9.2 Calibration Rules

- Flag models when ECE exceeds configured thresholds.
- Use calibration metrics for promotion criteria.
- Maintain calibration reports in model metadata.

## 10. Explainability

### 10.1 SHAP

- Use SHAP values to quantify feature impact on each prediction.
- Store top feature contributions in `explanation_summary`.
- Display explanations in UI dashboards.

### 10.2 Feature Importance

- Track global feature importance across models.
- Use importance metrics for model review and feature pruning.

### 10.3 Decision Rationale

- Provide prediction rationale for home/draw/away probabilities.
- Surface the strongest features and expected goal drivers.

## 11. Simulation and Scenario Analysis

### 11.1 Monte Carlo

- Run Monte Carlo simulations to estimate scoreline probabilities.
- Use repeated sampling of Poisson or bivariate distributions.
- Collect convergence and variance metrics.

### 11.2 Scenario Inputs

- Support explicit adjustments for injuries, rest days, and lineups.
- Store scenario metadata in audit records.

### 11.3 Simulation Outputs

- Sample size, win/draw/loss rates, goal expectations.
- Scenario comparisons and confidence intervals.

## 12. Dynamic Elo and Player Ratings

### 12.1 Dynamic Elo

- Maintain dynamic Elo scores for teams updated after each match.
- Use Elo as a predictive feature for team strength.
- Adjust home advantage and competition stage dynamically.

### 12.2 Player Ratings

- Store player status and rating as optional features.
- Use player availability for scenario simulation and lineup sensitivity.
- Enable future work on player-level predictions.

## 13. Continuous Learning

- Track drift in model performance across live predictions.
- Trigger retraining when performance degradation or calibration drift appears.
- Use dataset snapshots to reproduce training conditions.
- Periodically retrain models with fresh data while maintaining governance records.

## 14. Model Governance

### 14.1 Version Control

- Model artifacts, hyperparameters, and evaluation metrics are stored with each `ModelVersion`.
- Use immutable version identifiers and release notes.

### 14.2 Promotion Criteria

- Draft models require internal validation.
- Staging models require backtest and governance review.
- Production models require approval and documented metrics.

### 14.3 Rollback and Retirement

- Retired models remain accessible for audit.
- Rollback is supported by selecting prior stable `ModelVersion`.
